# R9700とV620の処理時間差の追加診断

2026年10月11日。GPU最適化検証でR9700の全体処理時間がV620より長かった理由を調べた。**R9700のGPUカーネル実行時間は短い。現在の負荷では、細かい処理の投入・同期・実行系の待ちに時間がかかり、GPU演算の速さが全体速度へ十分に反映されていないと考えられる。特定のROCm内部処理が原因だとまでは特定していない。**

## 測定条件と再計測

前回はV620をCPU16–19、R9700をCPU32–35へ固定していた。最適化前後の比較には使えるが、GPU間の性能差の解釈にはCPU配置が混ざる。今回のGPU測定は順番に実行し、同じCPU16–19で比較した。初期保存・形状・学習内容は前回と同じ。3世界・96体生存・容量合計384、32tickのウォームアップ、出生前の160tickを5回測り、中央値を使用。表示・保存・コンパイル初回・profiler・数値検査は定常時間から除く。

| 同じCPU16–19での最適化実行 | V620 | R9700 |
| --- | ---: | ---: |
| FP32、最初のプロセス | 5.909ms/tick | 5.908ms/tick |
| FP32、別プロセスで再実行 | 5.844ms/tick | 6.553ms/tick |
| BF16 | 6.157ms/tick | 6.272ms/tick |
| FP16 | 6.030ms/tick | 6.405ms/tick |

CPU32–35でも順番にFP32を測るとV620 5.903ms、R9700 6.697ms。メインスレッドだけをCPU16へ固定し、初期化済みの他スレッドはCPU16–19を許可する追加測定ではV620 5.884ms、R9700 6.513msだった。R9700のこの測定の各反復は6.541、6.536、6.513、6.030、5.885msで、同じプロセス内にも変動がある。

最初の同CPU比較では差が消えたが、再実行では残った。したがって「CPU配置の違いだけが原因」「同CPUにすれば安定して同速」とは結論しない。CPU周波数のgovernorはpowersaveで、CPU/GPUのクロックは固定していない。背景負荷・スケジューリング・周波数・実行系の寄与は分離できていない。測定順もランダム化していない。

## GPU演算と処理の間の空き時間

最初の同CPU16–19・FP32プロセスで、通常の速度測定とは別に12tickをprofileした。下表の「GPUカーネル実行」はカーネル時間区間の和集合、「空き時間」は最初のカーネル開始から最後の終了までの間にカーネルが走っていない時間。

| profiler中、1tickあたり | V620 | R9700 |
| --- | ---: | ---: |
| GPUカーネル実行 | 5.712ms | 3.271ms |
| カーネル間の空き時間 | 6.122ms | 7.479ms |
| 最初のカーネルから最後まで | 11.835ms | 10.750ms |
| GPUカーネル数 | 187 | 187 |

R9700はGPU上の処理を早く終える一方、カーネル間の空き時間が長い。通常計測の全体時間が両方約5.91msだったことと合わせると、現在の負荷ではGPU演算時間を短縮しても全体時間が同じ割合で短くなる状態にはなっていない。

**profilerはCPU処理や起動の時間を増やす。上表は通常計測の時間から差し引けず、空き時間の割合をそのまま本番のCPU律速率とも解釈できない。** 空き時間にはCPU側の仕事、処理投入・スケジューリング、依存関係や同期の待ち、計測の影響が含まれる。メインスレッド固定の追加profileでは影響がさらに大きくなったため、通常速度の推定には使用しない。

## 実装上の理由と未特定の部分

- 個体ごとに重みが独立しているため、`linear()`は`[個体, 1, 入力] × [個体, 入力, 出力]`という小さな行列積をまとめて実行する。共有モデルへの大きなミニバッチとは異なり、各行列の行数は1。現在の規模ではGPUの大規模な行列演算能力だけで速度は決まらない。
- 最適化後も1tickあたり187回のGPUカーネル起動が残る。推論・学習・観測・世界更新の間にPython、autograd、ライブラリ呼び出しが挟まる。
- 出生検出の`Learners.inherit()`が毎tick `mask.nonzero()`を呼ぶ。出生がないtickにもGPUとCPUの同期を伴う。`nonzero()`がhost-device synchronizationを起こすことは[PyTorch 2.12の説明](https://docs.pytorch.org/docs/2.12/generated/torch.nonzero.html)にも記載されており、今回も毎tickの`aten::nonzero`と`hipMemcpyWithStream`を確認した。
- 同CPUのFP32 traceでは、`aten::bmm`のCPU側の包含時間は1tickあたりV620 0.779ms、R9700 1.956msだった。GPUの行列演算自体はR9700の方が短い。R9700の行列演算呼び出し経路には追加の負担があることを示唆するが、包含時間には内部処理・待ち・profilerの影響があり、ライブラリ固有の原因を証明する値ではない。
- BF16/FP16でも重み・Adamの状態・多くの要素演算・物理はFP32を維持する。型変換などが増え、カーネル数はBF16 197回、FP16 206回。低精度化は処理投入や同期を減らさないため、その部分が律速なら追加利益は小さい。

`ROCBLAS_USE_HIPBLASLT=0`の短いFP32測定も行ったが、R9700 6.547msで、隣接する既定設定の再測定6.553msに対する改善はなかった。AMDの[rocBLAS設計説明](https://rocm.docs.amd.com/projects/rocBLAS/en/latest/conceptual/rocblas-design-notes.html)はGEMMのバックエンド選択とこの環境変数を説明する。ただし今回の設定変更だけでは、PyTorchを含む全経路の実バックエンドを独立に確認できていない。保存先の`r9700-cpu16-tensile`は環境変数を試したケース名であり、Tensile使用を実証したという意味ではない。hipBLASLt、rocBLAS、ドライバの特定の不具合を原因とは断定しない。

次に調べる価値が高いのは、毎tickのCPU同期の削減と、起動をまとめるHIP Graph、独立世界を多くまとめた場合の速度。AMDも、短いカーネルではフレームワークの準備・起動時間が演算時間を上回り、[HIP Graphがその繰り返し負担を減らす](https://rocm.docs.amd.com/projects/HIP/en/latest/how-to/hip_runtime_api/hipgraph.html)と説明している。出生処理などの可変長の操作があるため、現在のループ全体をそのままGraph化できるとは想定しない。これらの変更や世界数を増やす検証は今回まだ実施していない。
